### Why the Undo window dies in a one-match stage

This is the finding most likely to be met again. The web's `isCarriedForward` has no time window and no exemption for the
writer, so the deciding tap of a one-match stage, or of a knockout that feeds the next round, carries the result forward
at once and every later new write, the phone's own 45 s Undo included, is refused with `403 RESULT_CARRIED_FORWARD`
(`scoring.ts:611-625`; a keyed replay of a write the web already holds is still answered). The owner's divisions held
two singles matches and one doubles match, and he confirmed that Undo works with several matches in a stage. The
diagnosis is from the web's code; whether the "Result carried forward" card now appears on a real staging match was not
looked at in this session (device-only, below).

## Known limits and parked minors

Known limits, accepted:

- `base` counts score events, not the score. A co-scorer's Undo plus a mid-game partial game summary nets to zero, and a
  stale `serving` stamp is kept. It needs a mid-game score entry from the web inside the same window (the controller's
  ruling; the owner may correct it).
- A resend whose first copy the server stored but the ledger read has not caught up on is judged as a first send; the
  stamp may go without `serving`. The web matches by key and never compares payloads, so it is harmless. Not re-proved
  against the web.
- The 13 returns point is sent at once, the reason chosen before the tap; the web adds the returns after the point. Its
  payload carries no `server`, so a doubles returns point is not in the server's serve tally (the web's dock is the same).
- A doubles side with a bench row shows the side, not the player, until the web sends `slot` (low priority: the owner,
  "Singles and pairs only", 2026-11-04).
