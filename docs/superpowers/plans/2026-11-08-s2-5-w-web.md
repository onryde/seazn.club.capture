# S2-5 W — the web half of football Remote Scoring: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One `onryde/seazn.club` PR that (A) gives the device link's bootstrap each lineup row's team-sheet fields, for football and cricket, and (B, C) makes the console's football clock follow the shared clock and show match time.

**Architecture:** (A) is a read-model widening in `device-link-bootstrap.ts`, its zod schema and the generated OpenAPI; no new query, since `getLineup` already returns every field. (B) is three pure pieces: a server-time offset from the HTTP `Date` header, kept by the pad's transport; `latestClockAnchor` + `followAnchor` in the leaf `v3/clock.ts`; and a `reconcileClock` the host calls instead of `reseatClock`. The follow applies only when the skin's `PadClockSpec` says `shared: true`, and only football's does, so every other clocked sport (hockey, ice hockey) is byte-identical. (C) is a pure `matchClock(at, cfg)` beside the football skin, handed to the bar through `PadClockSpec.display`. Nothing changes in `formatClock`, the events route, the engine or the database.

**Tech Stack:** Next.js app `apps/web` (vitest `environment: "node"`, Playwright), zod, `@seazn/engine` = `@onryde/seazn-engine@^3.0.2` (football module identical to the phone's 2.0.0 pin, design §4), Postgres for the route test.

**Spec:** `docs/specs/2026-11-07-s2-5-football-design.md` in seazn.club.capture (approved 2026-11-08): §10 (the web side), §7.2 (shared clock, ruling 107), §7.4 (match time, ruling 108), §7.5, §4, §11 items 1 and 5. Rulings 103, 107, 108.

## Review Focus

1. **Two screens tap clock controls in the same second.** The ledger's order decides, and both screens end on the later seq's anchor, including when your own tap is still pending under a guessed seq that collides with a foreign row. Pinned in Task 3: `latestClockAnchor: at an equal seq the ledger's row beats this pad's pending guess`, and `two pads converge on the later of two near-simultaneous taps`.
2. **Undo of the newest clock event (a voided Start).** The anchor falls back to the clock event before it, and the console re-seats to it rather than keep running. Pinned in Task 3: `followAnchor: a void that moves the anchor BACK re-seats to the older event`.
3. **A browser clock that is minutes wrong.** Before any `/events` call there is no `Date` sample, so foreign anchors read on the device clock. After one call, the shared time is used. Pinned in Task 2: `serverOffsetMs is null until an /events response with a Date header`, and in Task 5's e2e skew step.
4. **A followed reading below the fold's `asOf`.** For example, a phone's offline-queued goal stamped later than the shared anchor implies. The console's next stamp, and its own Pause or Correct publish, must not go below `asOf`, or the server refuses them (`NON_MONOTONIC_TIME`). Pinned in Task 3: `stampOf with a same-period floor never stamps below it`, and in Task 5: `publishClock floors its at like a tap does`.
5. **A cfg the console folds with that has no extra time, while a ledger stamp names `ET_H1`** (cfg edited after play), or a mini-soccer cfg with uniform `periodSeconds`. Match time falls back to period-relative `M:SS` for an unknown period, and ignores a uniform override. Pinned in Task 4: `matchClock: an unknown period reads period-relative` and `uniform periodSeconds is ignored, as the engine does`.

## Task 2: Server time on the pad's transport, from the `Date` header (ruling 107; F1)

**Decision (the plan's, under ruling 103):** the offset is sampled from the HTTP `Date` header of the transport's two `/events` calls (POST append, GET `listEventsSince`). A sample is `Date.parse(date) + 500 − (sentAtMs + receivedAtMs) / 2`: the header's whole second plus half a second, against the request's local midpoint. The offset is the median of the last 5 samples. A sample whose round trip is negative or longer than 5000 ms is dropped.

`/state` and `/rules` are not sampled. `/state` revalidates by ETag (`server/usecases/fixtures.ts:955-960`), and a revalidated fetch can hand back a stored response's headers.

**Rejected option, with its reasoning:** add `recorded_at` to the append answer. It is millisecond-exact, and the phone design assumed it. But it changes the events route the design keeps fixed (§10). It needs a new idempotency-cache prefix (`scoring.ts:72-79`: `idemv3` → `idemv4`, two tests). It needs a durable-replay field (`engine-db/replay.ts:45-72`). And a replayed answer's `recorded_at` is the original write's, which would poison a sample unless replays are told apart. The `Date` header needs none of that. Its ±0.5 s quantisation, medianed over 5, sits well inside §11's "within a second". If the owner prefers exactness, this is the place to switch, and Task 3's anchors do not change.

## Task 4: Match time for football (ruling 108; design §7.4)

**The rule.** Restated from the engine and pinned by the vectors below.

Period order is `H1, H2`, or `H1, Q2, Q3, Q4` when `halves === 4`, then `ET_H1, ET_H2` when `extraTime.enabled`. A period's nominal length comes from F8's rule. Its start is the sum of the lengths of the periods before it.

For `at = {period, elapsed}`:

- If the period is unknown to the cfg, the reading is `formatClock(elapsed)`.
- If `elapsed <= length`, it is `formatClock(start + elapsed)`.
- Otherwise it is `` `${Math.floor((start + length) / 60)}+${formatClock(elapsed - length)}` ``: the time passed in
  added time, minutes and seconds.

The clock face shows the time **passed** in added time, `90+2:30` at 92:30 (ruling 109, owner, 2026-11-08: "A"). An
event's minute label is the minute being played (`90+3'` for the same moment), as football counts a goal at 0:30 as
the 1st minute; labels are the phone's and the console's event copy, not built here.
